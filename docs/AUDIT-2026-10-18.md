### C4 — `update()` repositori menulis `undefined` ke kolom nullable (kehilangan data diam-diam)
**File:** `apps/server/src/db/repositories/agents.ts:113–116`, `tasks.ts:107`, `projects.ts:112`.
**Bukti:**
```js
// agents.ts:113–116
.name = name ?? agent.name,
.title = title ?? agent.title,
```
Operator `??` hanya melewati `null` dan `undefined`. Karena `z.object` Zod secara bawaan **menghapus** properti yang tidak dikirim, `name: undefined` tidak akan pernah mengisi fallback — `undefined` dilewatkan ke `set`, kolom jadi `NULL`.
**Konsekuensi:** `PATCH /api/agents/:id` dengan hanya `{ "title": "Ketua" }` **mengosongkan kolom `name`**. Sama untuk `title`, `skills`, `avatar`. Berlaku juga di `tasks.ts:107` (`assignee_agent_id`) dan `projects.ts:112` (`name`, `description`).
**Perbaikan:** `??` tidak cukup. Pisahkan `undefined` (tidak dikirim) dari `null` (sengaja dihapus):
```js
const coalesce = <T>(incoming: T | undefined, current: T | null): T | null =>
  incoming === undefined ? current : incoming;
.name = coalesce(name, agent.name),
```
+ test: kirim `{ title: 'Ketua' }` saja, kolom `name` harus tetap berisi nilai lama.
**Test:** tambah case di `agents.test.ts`, `tasks.test.ts`, `projects.test.ts`.

### C5 — Dispatcher menjalankan tanpa batas waktu (potensi runaway)
**File:** `apps/server/src/services/dispatcher.ts` (`runInternal`, `runWithTimeout`, `dispatchTask`), `apps/server/src/services/hermes/real.client.ts`.
**Bukti:** `runInternal()` memanggil `runWithTimeout(task, 900000)` — **tapi tidak ada yang memanggilnya.** Yang dipanggil adalah `dispatchTask()` → `hermes.client.runTask(task, agent, context, runTask)`, dan `real.client.ts` tidak pernah menyimpulkan `runTask`.
Akibatnya `internal.runTask` (120000 ms) tidak pernah tercapai, dan `HERMES_TIMEOUT_MS` (300000 ms) hanya berlaku untuk handshake — bukan untuk stream. Stream yang tidak pernah berakhir berarti task berjalan selamanya.
Perilaku ini ada di dua tempat berbeda (`internal: 120000ms` vs `runWithTimeout: 900000ms`) — duplikasi.
**Perbaikan:** di `real.client.ts`, bungkus handler `runTask` dengan `AbortSignal.timeout` + timeout stream:
```js
const result = await runTask(task, agent, context);
```
→ bungkus dengan timeout internal 900000 ms + `AbortController`, dan rapikan `runInternal` supaya tidak lagi menyimpan timeout duplikat.
**Test:** mock runTask yang tidak pernah resolve → timeout throw setelah 900 detik (mock timer).

### C6 — Tidak ada graceful shutdown
**File:** `apps/server/src/server.ts` (`app.ready()`, `listen()`), `apps/server/src/index.ts`, `apps/server/src/services/media.ts`.
**Bukti:** `server.ts` — tidak ada `SIGTERM`/`SIGINT` handler. `index.ts` hanya menjalankan `startPeriodicHealthChecks(60000)` — tidak pernah dihentikan. `media.ts` (`startMediaSweepTimer`) juga tidak pernah dihentikan. Ketika menerima `SIGTERM`, Docker kirim `SIGKILL` setelah 10 detik — timer dan konteks berjalan tidak terputus dengan bersih.
**Perbaikan:**
```js
const shutdown = async () => {
  await app.close();      // flush Fastify
  closeDatabase();        // commit WAL
  dispatcher.destroy();   // stop health check
  stopMediaSweepTimer();  // stop sweep
  process.exit(0);
};
process.on('SIGTERM', shutdown);
process.on('SIGINT', shutdown);
```
+ `media.ts`: export handle, tambah `stopMediaSweepTimer()`.
+ `index.ts`: simpan ref interval, panggil `clearInterval` di shutdown.
**Test:** `kill -TERM <pid>` → log "shutdown complete" dalam < 5 detik.
